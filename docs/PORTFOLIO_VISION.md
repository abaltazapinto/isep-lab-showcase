# Engineering Portfolio — Vision

## Purpose

This repository is evolving into a long-term engineering portfolio. It should make engineering work understandable through problems, working systems, experiments, decisions, debugging, validation and documented results.

This is the single authoritative portfolio-wide vision. Programme-specific documents provide academic context under this vision; they do not define a separate portfolio architecture.

## Scope

The portfolio supports academic engineering work from the ISEP Embedded Engineering postgraduate programme, a master's in Critical/Computational Critical Systems, and future academic work. It also supports Personal Engineering Labs.

Personal-lab scope includes Raspberry Pi/Linux, Proxmox virtualization, Pi-hole/DNS, Nextcloud/self-hosting, Tailscale/remote infrastructure, networking and security investigations, CCTV, and ESP32/IoT/automatic irrigation experiments. These are areas of interest, not claims that systems have been implemented or validated.

Engineering domains include Embedded Systems, Critical Systems, Embedded AI, Cloud & Distributed Systems, Infrastructure & Reliability, Networking & Security, and IoT where appropriate. Academic origin and engineering domain are separate concepts. Their definitions belong to the [content architecture](architecture/ARCHITECTURE.md).

## Core principle

> Show engineering evidence, not a list of technologies, courses or software installations.

The preferred case-study narrative is:

Problem → Architecture → Implementation → Engineering decisions → Failure/debugging → Validation/testing → Evidence → Lessons learned

Installation alone is not sufficient evidence of an engineering case study. The value comes from explaining the problem, reasoning about the system, investigating its behaviour and showing what supports the conclusions.

Unknowns, failed experiments, limitations and missing measurements must remain explicit. Planned work must remain distinguishable from completed work. The portfolio must not claim undocumented achievements.

## Long-term direction

Academic learning and personal experimentation should progressively produce engineering cases that another engineer can assess. Course names, grades and technologies provide context; the case and its evidence carry the engineering argument.

Cases may grow incrementally. A documented failed experiment can be valuable, and incomplete evidence should guide the next investigation rather than be replaced with an assumed result.

The [project standard](architecture/PROJECT_STANDARD.md) defines reporting requirements. The [ISEP academic context](academic/ISEP_VISION.md) describes that programme's learning and project direction. Future programme documents should be added when there is enough verified content to give them a useful responsibility.
